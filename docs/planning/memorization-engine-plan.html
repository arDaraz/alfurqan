Memorization Engine Plan

Technical implementation plan for the memorization engine (live recitation checking) in the alfurqan app. Grounded only in the current source code: the verification services, the playback engine, the mushaf renderer, and the seed scripts. Tajweed assessment lives in its own plan, the Tajweed Assessment Plan.

Core rule of the whole plan: evaluation compares normalized Unicode words keyed by surah:ayah:position. Page fonts and glyph codes (codeV2) stay a rendering concern and never enter the matcher. Phase 2: Memorization engine

Goal: the user selects a surah to recite and practice it. The app follows word by word, flags wrong, skipped, repeated, and reordered words, highlights the current word in the active layout, gives haptic feedback, and reports session accuracy. The engine internally works on any word range, so ayah-range and page scopes can ship later without rework, but the product surface for this phase is surah selection.

2.1 Reference word data

Goal: one layout-independent table of per-word Uthmani text with precomputed normalized form.

  • New seed table quran_words(surah_number, ayah_number, word_position, text_uthmani, text_normalized), sourced from the same upstream as the ayah text.
  • text_normalized is computed at seed time with the existing normalizeQuranText, so runtime never normalizes reference text.
  • Seed-time validation: per ayah, the word count must match the max word position with char_type='word' in both layout tables. A mismatch fails the seed, not the runtime.
  • New repository function getExpectedWords(scope) returning { key, textUthmani, textNormalized }[]. Surah scope is what this phase ships; the function also accepts an ayah range or page so later phases need no rework.

Verify: seed passes validation for all 6,236 ayahs, and a unit test proves the scope loader joins cleanly against both layouts.

2.2 Audio capture and ASR

Goal: streaming Arabic transcription on device with one native dependency.

  • whisper.rn (whisper.cpp binding). Its realtime transcriber covers mic capture, voice activity detection, and streaming transcription in one module. Needs prebuild, an iOS mic permission string, and Android RECORD_AUDIO.
  • Model strategy: bundle a small quantized model, download a larger one on demand, copying the download pattern from ayahAudioCache.
  • 16 kHz mono. VAD silence events double as the long-pause detector.
  • Rejected: OS speech recognizers. Their language models target modern Arabic, cannot be constrained to Quranic vocabulary, and some routes leave the device.
  • Audio session rule: listening and playback are mutually exclusive. Starting a session stops RecitationEngine and switches the audio mode to record, and reverses that on stop.

Verify: the go/no-go spike (milestone 1) logs latency and memory on a real iPhone and a mid-range Android against a hardcoded Al-Fatiha scope.

2.3 Alignment engine

Goal: turn noisy transcript tokens into confident word-level decisions. Pure TypeScript, extending the existing matcher, fully unit-testable.

  • Fuzzy equality. Replace exact match with the existing Levenshtein ratio (tokenConfidence) at a configurable threshold near 0.75.
  • Sliding window. Compare each observed token against expected[i - backtrack .. i + forward]. The best-scoring window position decides the classification.
  • Stability gating, two speeds. Whisper partials mutate, so the engine runs two decision lanes. The fast lane advances the current-word highlight from streaming partials, so the pointer keeps pace with fast recitation at sub-second latency. The slow lane commits error flags only from final segments, and an error must survive the next segment before it fires haptics (two-strike rule). Until then the word shows the uncertain state. Target: error flags land within about 1.5 seconds at a normal pace; the spike measures the real number and tunes segment length against it.
  • Pause tolerance. The user may pause or hesitate between words. Silence is never an error: on a VAD silence event the engine holds the pointer and waits for the voice to return, and only past a long configurable threshold does it give a gentle optional nudge.
  • Multi-word repetition. Match runs of tokens, not single tokens, so a repeated phrase is one event.
  • Every event carries a confidence so the feedback layer can suppress weak corrections.
flowchart TD
  T[Observed token] --> W{Match in window?}
  W -->|at pointer| OK[Correct, advance]
  W -->|elsewhere| POS{Ahead or behind?}
  POS -->|ahead| SK[Skipped words, jump]
  POS -->|behind| RP[Repetition]
  W -->|no match| SIM{Similar to expected?}
  SIM -->|yes| SUB[Substitution]
  SIM -->|no| ADD[Addition, hold pointer]

Verify: fixture tests replay recorded transcripts of correct recitation, a skip, a repeat, and a substitution, and assert the emitted event sequence. The ASR itself is the only part that needs a device.

2.4 Session engine and state

Goal: one service owns the session lifecycle, one store feeds the UI.

  • New service PracticeEngine, parallel to the playback RecitationEngine: loads scope words, owns the whisper session, feeds finals to the matcher, applies the confidence policy, drives the store and the WebView.
  • New transient Zustand store practiceStore: session status, current word key, per-word state map, event list, elapsed time. Same pattern as recitationStore.
  • Persistence in the existing SQLite database: practice_sessions and practice_events. Raw audio is stored only when the user opts in.
Session schema draft 
practice_sessions(id, scope_type, scope_start_key, scope_end_key,
                  started_at, ended_at, asr_model_version, accuracy)

practice_events(id, session_id, timestamp_ms, event_type,
                word_key, observed_text, confidence)

event_type: word_correct | substituted | skipped | repeated
          | added | jump | pause | uncertain

Verify: a full session on the practice screen survives start, pause, stop, and app background without leaking the mic or the audio session.

2.5 Highlighting in the active layout

Goal: word states render identically in the Madani glyph layout and the IndoPak Unicode layout.

  • Add window.setPracticeStates(states) to mushafHtml.ts next to setPlayingAyah, keyed by data-wk: current, correct, wrong, skipped, uncertain.
  • Both renderers emit the same spans, so one API covers both layouts by construction.
  • The engine injects diffs (changed keys only) and throttles to one injection per matcher decision, never per partial.

Verify: visual check on the iOS simulator in both layouts, same session, same states.

2.6 Feedback, accuracy, and report

  • Haptics via expo-haptics: substitution medium, omission double light, jump heavy, pause a light periodic nudge, uncertain nothing. Fired by the engine only on committed errors. Visual state is always the fallback.
  • Global app settings: a haptics on/off toggle plus a haptic intensity control (light, medium, strong) that scales every pattern.
  • State legend: a short first-session explainer teaches the word colors (current, correct, wrong, skipped, uncertain), and a legend stays reachable from the practice screen during any session.
  • Accuracy = correct / (correct + substituted + skipped) over the attempted range, computed from the event log at session end.
  • Session report screen lists errors by ayah and word with deep links to the word's page.
  • Self-review replay: when audio storage is on, the saved session keeps per-ayah recordings, and the report plays back the user's own recitation at each mistake so they can hear where they fell down.

Phase 2 order of work

  1. Spike (go/no-go): whisper.rn in the dev build, latency and memory measured on real devices. The spike pins one fixed test surah internally only because the surah picker does not exist yet; the shipped feature (milestone 4) lets the user pick any surah.
  2. quran_words seed, validation, scope loader.
  3. Matcher upgrade with fixture tests.
  4. PracticeEngine, store, surah picker, practice screen wiring, WebView word states.
  5. Haptics, legend, session report with replay, persistence, accuracy.

Open questions

Which speech-recognition model should the app use?

Two kinds of Whisper model can run on the phone. The general model is the standard one trained on everyday speech in many languages. The Quran model is the same engine retrained by others on Quran recitation, so it should hear recitation better, but that claim is unproven on our devices. "Test both first" means milestone 1 builds one small throwaway test screen, runs the same recitations through both models on a real iPhone and a real Android, and the measured accuracy and speed decide which model ships.
