Tajweed Assessment Plan

Technical implementation plan for tajweed (pronunciation) assessment in the alfurqan app. Split out of the Memorization Engine Plan because the two are separate engines: memorization checking is text alignment, tajweed assessment is acoustic analysis. Everything here depends on the memorization engine shipping first.

Phase 3: Tajweed assessment

Goal: after a session, show which expected tajweed rules were likely applied and which need review, without overclaiming. Separate engine and data, running only on words Phase 2 confirmed as textually correct. A word that is not text-aligned is not evaluated, never wrong tajweed.

3.1 Rule reference data

  • Seed table tajweed_rule_instances(id, word_key, rule_type, char_start, char_end, params_json) from a tajweed-annotated Uthmani source for Hafs. params_json holds rule parameters such as the expected madd length in harakat.
  • Seed-time validation cross-checks each instance's characters against quran_words.text_uthmani.
  • All rules are seeded. A separate in-code registry declares which rule types the current detector version supports, so unsupported rules are never shown as failed.

3.2 Displaying expected rules

  • Word inspector first: tap a word (or a flagged word in the report) to see its rule instances with names and short explanations. No audio work needed, and it is immediately useful for study.
  • Glyph recoloring in the QCF layout is deferred. Span-level coloring in the IndoPak Unicode layout can come later from char_start/char_end.

3.3 Assessment pipeline (after-session only)

  • With tajweed enabled, keep per-ayah audio (opt-in) plus whisper word timestamps from the Phase 2 session.
  • Segmentation spike: whisper word timestamps are too coarse for phonemes. Evaluate a small quantized CTC phoneme model through ONNX Runtime for forced alignment, with DTW over whisper token timestamps as the cheap first cut. Phoneme timing quality decides everything downstream.
  • One detector module per rule family, each with its own confidence and its own precision gate.

  • Output states per rule instance: passed, possible issue, not evaluated, low confidence, unsupported. Feedback copy never claims certainty ("possible short elongation, review this word").
  • Scores count only evaluated, supported instances in the denominator.

3.4 Teacher validation loop

Gate before any rule ships:

  • Export flagged and passed segments (audio clip, word, rule, verdict) as a review bundle.
  • Qualified teachers label each verdict correct or wrong.
  • Per-rule precision decides release, and thresholds are tuned against this set. In-app "this feedback was wrong" disputes feed the same loop.

Phase 3 order of work

  1. Rule data seed plus word inspector UI.
  2. Segmentation spike: forced alignment quality on device.
  3. Madd detector, after-session report, segment replay.
  4. Teacher validation tooling, then ghunnah and qalqalah behind the supported-rules registry.
